# 团队 AI Token 管理平台（team-router）

## Problem
企业内部团队使用多家 LLM 服务（OpenAI、Anthropic 及其他兼容上游）时，成员各自申请、保管 API Key，用量与费用分散在各个上游账号里：管理者无法按部门核算支出、无法给部门/个人设预算上限，Key 泄露与滥用难以及时发现和止损。现成开源方案（如 new-api）面向对外运营的多租户场景，缺少组织结构（部门树）、组织级预算管控等内部治理能力，不能直接作为团队内部平台使用。

## Evidence
- `docs/api/` 下 10 篇完整 API 规格（2026-10-27 更新）已覆盖中继、认证、用户自助、用户/部门/Key/渠道/价目/日志统计管理，后端各域代码与数据库迁移已落地——团队已按此方向实际投入并持续推进。
- 痛点本身（散 Key、费用黑箱、无部门核算）。

## Users
- **Primary**：内部平台管理员（IT / 基础设施负责人）。触发场景：为团队开通或收回模型访问、按部门分配预算、查看与核算各部门/各渠道的 AI 支出、应对成员离职或 Key 泄露。
- **Secondary**：团队成员（开发者与日常使用者）。触发场景：获取一个可用的 Key 调用模型、查看自己用了多少、确认剩余额度。
- **Not for**：对外 SaaS 多租户运营、向外部客户按 token 计费转售的场景。

## Hypothesis
We believe **统一的多 provider 中继网关 + 部门/用户两级预算管控** will **消除成员散 Key 与 AI 支出黑箱，让支出按部门与个人可视、可控** for **企业内部团队**。
We'll know we're right when **团队内 LLM 调用基本全部经网关进行（不再新增直连上游 Key），且每个部门与用户的当期用量、剩余预算可在系统中查询，预算超限后不再产生新的成功请求**。

## Success Metrics
| Metric | Target | How measured |
|---|---|---|
| 网关接管率 | ≥ 95% 内部 LLM 调用经网关 | 上游账单与网关日志汇总对照，直连账单占比 |
| 预算执行有效性 | 预算耗尽后成功请求数 = 0 | 日志对账（超限后应全部返回 429 拒绝） |
| 用量可视性 | 任意请求可按 部门 / 用户 / 模型 / 渠道 检索归集 | 验收演示：管理台检索 |
| 开通效率 | 新成员从创建到可调用 < 5 分钟 | 管理操作计时 |

## Scope
**MVP** — 后端能力闭环 + 一个试点部门验证假设：多 provider 中继（OpenAI / Anthropic 兼容入口、协议任意互转、priority/weight 调度与跨渠道重试）、Key 级与用户级额度、部门树与成员归属、**部门级预算**（超限拒绝或告警，语义见 Open Questions）、按部门/用户/模型/渠道维度的日志与统计查询。验收标准：API 层完成 + 试点部门真实流量运行。

**Out of scope**
- 充值 / 支付 / 邀请注册 / 分销等商业化能力 — 内部使用，预算由管理员行政分配，不向用户收费。
- 多租户 SaaS 隔离与租户自助开户 — 单一企业内部部署。
- 按 Key / 按用户的 QPS 限流 — 预算已约束成本，速率治理后置（试点出现滥用再评估）。
- 内置模型市场 / prompt 市场 — 与内部管控平台定位无关。

## Open Questions
- [ ] **部门预算语义**：一次性额度池还是按周期（如月度）重置？超限是硬拒绝（中继返回 429）还是仅告警，还是两者按部门可配置？——月度重置
- [ ] **部门预算沿树聚合**：部门预算是否沿部门树向上聚合约束（子部门受父部门预算约束）？——沿树聚合
- [ ] **多部门归属的用量归集**：用户同属多个部门时，一次请求的用量记入哪个部门（主部门？）——M2 最高层次部门，多个同级部门时个人页面可以获取多个apikey
- [ ] **SSO 目标提供方**：企业微信 / 飞书 / 钉钉，哪一个（或哪几个）是上线硬性要求？飞书
- [ ] **审计与合规要求**：管理操作审计日志是否为内部合规硬性要求？日志保留期限多久？ 180 天
- [ ] **接管率度量手段**：能否通过网络策略禁止直连上游，使「网关接管率」可度量、可执行？ 暂时不需要
